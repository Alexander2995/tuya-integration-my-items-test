# my-items × Tuya — локальное демо

Предмет **«Кластер К12»**, параметр **«Потребляемая мощность»**, единица **Вт**. Java 17, Spring Boot 4.1.2, Maven. HTML/CSS/JavaScript отдаёт тот же сервер. Node.js и Docker не нужны.

## Быстрый запуск в Windows / PowerShell

Откройте PowerShell в каталоге этого проекта, рядом с `pom.xml`:

```powershell
java -version
javac -version
mvn -version
# Выполните копирование, только если tuya.local.properties ещё не существует:
Copy-Item -LiteralPath .\tuya.local.properties.example -Destination .\tuya.local.properties
notepad .\tuya.local.properties
mvn spring-boot:run
```

Откройте **http://localhost:8080**. Остановка — **Ctrl+C** в окне запуска. Сервер привязан к `127.0.0.1`; из сети он недоступен. При первом запуске Maven скачивает зависимости из Maven Central.

Перед сборкой новой версии остановите ранее запущенный JAR (`.\stop-demo.ps1`): Windows может блокировать замену используемого файла.

В подготовленной на этом компьютере копии `tuya.local.properties` уже записаны известные Client ID, Device ID и регион. Впишите **Client Secret** вместо `REPLACE_ME`, сохраните и перезапустите сервер. Не отправляйте заполненный файл в чат. Файл исключён из Git и не входит в JAR.

Конфигурация явно загружается штатным `spring.config.import=optional:file:./tuya.local.properties`. Это **не `.env`**. Файл ищется относительно текущей папки запуска, в том числе при запуске JAR. Изменения требуют перезапуска. Переменные среды с теми же именами имеют приоритет.

```properties
TUYA_CLIENT_ID=REPLACE_ME
TUYA_CLIENT_SECRET=REPLACE_ME
TUYA_ENDPOINT=https://openapi.tuyaeu.com
TUYA_DEVICE_ID=REPLACE_ME
TUYA_API_FAMILY=CLOUD_V2
```

Параметры находятся в **Tuya Developer → Cloud → Development → ваш проект → Overview / Authorization Key**. Device ID — вкладка **Devices**. Регион должен совпадать с центром данных устройства и проекта, а не со страной компьютера. Проверьте действующие подписки и права во вкладке **API Services**.

## Сборка, тесты, JAR

```powershell
mvn test
mvn clean package
java -jar .\target\tuya-local-demo-0.1.0.jar
```

Запускайте JAR из папки, в которой находится `tuya.local.properties`. Если порт 8080 занят, например:

```powershell
java -jar .\target\tuya-local-demo-0.1.0.jar --server.port=8081
# либо
mvn spring-boot:run '-Dspring-boot.run.arguments=--server.port=8081'
```

При переносе достаточно JAR, Java 17 и локального файла настроек; для JAR Maven не требуется. Упакованный архив исходников секретов не содержит. Логи по умолчанию не содержат тел запросов, заголовков, токенов или ключей. Не включайте HTTP wire logging и TRACE для проверки подключения.

Дополнительно есть запуск JAR в фоне без отдельного окна. Выполняйте из папки проекта:

```powershell
.\start-demo.ps1
.\stop-demo.ps1
```

После изменения конфигурации остановите и запустите приложение заново. Эти скрипты не меняют политику выполнения PowerShell. Если локальная политика запрещает `.ps1`, используйте обычный `java -jar` или `mvn spring-boot:run`. PID и логи фонового запуска находятся в `.runtime/`; остановка проверяет путь JAR перед завершением процесса.

## Семейства Tuya API

В присланном запросе использовано **Cloud Thing v2**, поэтому по умолчанию выбран `CLOUD_V2`. Приложение не перебирает API автоматически. Все запросы выполняются Java-сервером. Доступность всей группы API проверяется реальным чтением после настройки ключей; успешный `/state` сам по себе не гарантирует права на модель и свойства.

| Настройка | Информация | Спецификация | Показания | Команда POST |
|---|---|---|---|---|
| `CLOUD_V2` | `/v2.0/cloud/thing/{id}` | `/v2.0/cloud/thing/{id}/model` | `/v2.0/cloud/thing/{id}/shadow/properties` | `/v2.0/cloud/thing/{id}/shadow/properties/issue` |
| `DEVICES_V1` | `/v1.0/devices/{id}` | `/v1.0/devices/{id}/specifications` | `/v1.0/devices/{id}/status` | `/v1.0/devices/{id}/commands` |
| `IOT03` | `/v1.1/iot-03/devices/{id}` | `/v1.0/iot-03/devices/{id}/specification` | `/v1.0/iot-03/devices/{id}/status` | `/v1.0/iot-03/devices/{id}/commands` |

`{id}` берётся только из локальной конфигурации. Для Cloud v2 `model` декодируется из JSON-строки; читаются свойства стандартного сервиса `code=""`, их `typeSpec` и `accessMode`. Именованные сервисы требуют отдельного согласования адресации и этим демо автоматически не используются.

Команда Cloud v2 имеет форму `{"properties":"{\"<код_реле>\":true}"}`: `properties` является строкой JSON, как в официальной документации. Для двух семейств v1 используется `{"commands":[{"code":"<код_реле>","value":true}]}`. Точный код берётся из модели, а не фиксируется в шаблоне команды.

**GET `/state` не читает реле:** `state=0` означает, что устройство не заморожено; `state=1` — заморожено. Online/offline читается из `is_online` (Cloud v2) или `online` (v1).

Основные региональные endpoint:

| Центр данных | Endpoint |
|---|---|
| Центральная Европа | `https://openapi.tuyaeu.com` |
| Западная Европа | `https://openapi-weaz.tuyaeu.com` |
| Западная Америка | `https://openapi.tuyaus.com` |
| Восточная Америка | `https://openapi-ueaz.tuyaus.com` |
| Китай | `https://openapi.tuyacn.com` |
| Индия | `https://openapi.tuyain.com` |

## Показатели и неоднозначность

Числовое значение нормализуется как **raw × 10^(-scale)**, затем переводится в Вт / В / А / кВт·ч. Используется `BigDecimal`; в локальном JSON числа измерений передаются десятичными строками, чтобы JavaScript не вносил округление. Отсутствие значения, единицы или явного корректного `scale` даёт **«Нет данных»**. Ноль показывается только при реально полученном нулевом показании с корректными метаданными. Мощность из напряжения и тока не вычисляется.

Сначала ищутся стандартные коды `cur_power`, `cur_voltage`, `cur_current`, `add_ele`, при этом тип, единица и масштаб обязательно проверяются по модели конкретного устройства. Разные API могут возвращать для одного кода разные масштабы. Другой код можно явно выбрать в настройках:

```properties
TUYA_RELAY_CODE=
TUYA_POWER_CODE=
TUYA_VOLTAGE_CODE=
TUYA_CURRENT_CODE=
TUYA_ENERGY_CODE=
```

Реле выбирается автоматически только при единственном Boolean/bool свойстве `switch` или `switch_<номер>`. Для команд дополнительно требуется доступность записи в модели/спецификации. При нескольких каналах либо ином коде ничего не выбирается молча: задайте `TUYA_RELAY_CODE` по диагностике и назначению розетки. Enum, инверсные реле и упакованные raw/phase-данные автоматически не интерпретируются.

`add_ele` показан как **энергия — показатель устройства**. Этот код без дополнительных сведений не гарантирует накопительный счётчик за весь срок: период и смысл определяются конкретной моделью. Отсутствующий показатель не заменяется нулём. Произвольный числовой код с подходящей единицей автоматически не объявляется мощностью.

В Cloud v2 `properties[].time` показывается отдельно как время обновления/отчёта конкретного свойства, а не гарантированное время физического измерения. В v1, если такого поля нет, сообщается только время получения. Внешнее поле ответа `t`, `update_time` информации устройства и часы HTTP-запроса не используются как время измерения мощности.

## События Tuya: Message Queue / AES-GCM

Реализован исходящий клиент очереди сообщений Tuya. Отдельный сервер Pulsar и Docker на компьютере не нужны. Поддерживаются авторизация `auth1`, AES-GCM с проверкой тега, TLS с проверкой сертификата и имени сервера. Формат сверён с текущим официальным Java SDK Tuya (точный commit указан в `THIRD_PARTY_NOTICES.md`). Используется Apache Pulsar client 4.2.5, управляемый Spring Boot; старые зависимости примера Tuya не копируются.

В `tuya.local.properties`:

```properties
TUYA_MQ_ENABLED=true
TUYA_MQ_ENV=PROD
```

В примере конфигурации получение событий выключено, чтобы не запускать подписку до настройки. На этом компьютере оно включено. `PROD` — обычный канал; `TEST` — только если устройство назначено тестовым в Tuya. Для текущего региона используется `pulsar+ssl://mqe.tuyaeu.com:7285/`; нужен исходящий доступ к порту 7285. Входящие порты и публичный адрес не требуются. Используются те же серверные Client ID/Secret. REST access token для авторизации очереди не используется.

В кабинете Tuya включите Message Service и правила сообщений для нужной среды. Для legacy-протокола нужны отчёты `statusReport` (protocol 4), а при необходимости `online`/`offline` (protocol 20). Для IoT Core — `devicePropertyMessage`/`deviceQueryPropertyMessage` (protocol 1000), `deviceOnline`/`deviceOffline` (protocol 1001). Приложение распознаёт оба документированных формата, но включать одновременно обе группы одного события в кабинете не требуется. Не включайте фильтр только по `fault`, если хотите получать мощность.

Установленная подписка ещё не означает получение сообщений: на странице отдельно показаны соединение, число полученных и применённых сообщений, время последнего события этой розетки. Если счётчики остаются нулевыми, проверьте среду и правила; события могут приходить только при фактическом отчёте устройства. Для диагностики доставки Tuya предоставляет Cloud Development → Cloud Monitoring → Server-side Message Logs. Сообщения учитываются по тарифу Message Service; отключённый резервный опрос не отключает очередь.

После подключения очередь инициирует чтение модели и снимка через REST. Дальнейшие события применяются **без REST-запроса на каждое сообщение**: частичные показатели объединяются с последним снимком и нормализуются по той же модели Cloud v2. Дубликаты по `dataId` и более старые времена показателей игнорируются. Значения неизвестных кодов и сообщения без времени отчёта свойства не подменяются предположениями. Форматы v1 могут иметь другую нормализацию, поэтому очередь включается только при `TUYA_API_FAMILY=CLOUD_V2`.

Очередь работает всё время, пока запущено приложение, включая закрытую страницу. После разрыва выполняется переподключение с увеличением паузы до 60 секунд и сверка через REST. Необрабатываемые сообщения подтверждаются и учитываются отдельным счётчиком, чтобы не зациклить повторную доставку. Логи Pulsar отключены: они могут включать приватные имена топиков; тела, ключи и токены не печатаются.

Java-сервер передаёт снимки открытой странице через **SSE** (`GET /api/events`). Проверка изменившегося снимка раз в секунду выполняется только в памяти сервера и не опрашивает Tuya. При скрытии/закрытии страницы её SSE-соединение закрывается; серверная подписка продолжает работать. Состояния REST, очереди, розетки и связи страницы отображаются отдельно.

## Обновление и управление

При открытии страницы читается локальный снимок; если снимка нет и заполнена конфигурация, выполняется начальное чтение Tuya. Сервер получает события при включённой очереди. Резервный опрос выключен по умолчанию; доступен интервал **30–3600 секунд**, исходно 60. При подключённой очереди запланированный опрос пропускается; при её недоступности работает, если включён пользователем. Следующий цикл планируется после завершения предыдущего. При скрытии вкладки новые циклы приостанавливаются, при закрытии таймер удаляется, ожидающий запрос браузера отменяется (уже начатый запрос сервера может завершиться). Несколько вкладок используют общую серверную блокировку, показания младше 3 секунд переиспользуются.

Обычное обновление — два запроса (информация и свойства); спецификация кэшируется на 15 минут. Первое чтение — три запроса плюс получение токена. Токен хранится только в памяти и обновляется заранее по `expire_time` через refresh token. При явном истечении токена чтение повторяется один раз. Автоматических повторов команды нет. При квоте/HTTP 429 автообновление выключается. Квота и стоимость зависят от подписки проекта, проверьте Usage.

Команды отправляются только кнопками **«Включить» / «Выключить»**. Повторные действия блокируются на странице и сервере. Перед командой выполняется свежее чтение; известный offline запрещает отправку. После принятия командой облаком выполняются максимум три чтения с паузой 1,5 секунды; новые попытки начинаются только в пределах 8 секунд. Каждый сетевой запрос ограничен 10 секундами, поэтому суммарное ожидание с подготовкой может быть длиннее 8 секунд, но ограничено числом запросов.

Отдельно возвращаются `accepted` и `confirmed`. `confirmed` означает совпавшее показание после команды; если ранее было иное значение и API предоставляет время отчёта, оно должно измениться. Если целевое состояние было установлено раньше, интерфейс прямо сообщает об этом. Это подтверждение данных облака, а не независимая проверка электрического контакта. При отсутствии подтверждения или сетевой ошибке сообщается неопределённый результат. Команда автоматически повторно не посылается.

При неудачном обновлении последний успешный снимок сохраняется с отметкой ошибки. При offline облачные показания могут быть устаревшими. Диагностические блоки содержат **отобранные обезличенные поля**, а не полные сетевые ответы: numeric/bool значения, коды, типы, единицы, scale и время отчёта. Строковые значения скрываются; полная информация устройства (включая `local_key`, IP, координаты, идентификаторы) в браузер не передаётся.

## Ошибки

| Сообщение | Что проверить |
|---|---|
| Нужна настройка | Заполните четыре обязательных поля локально и перезапустите |
| Ошибка подписи / 1004 | Client ID/Secret, время Windows, регион проекта |
| Ошибка токена | Ключи/регион, права авторизации и срок сервиса |
| Нет прав / 1106 / HTTP 403 | API Services, срок подписки, привязка аккаунта, регион, семейство API |
| Квота / HTTP 429 | Usage, действующая подписка, интервал запросов |
| Розетка offline | Питание/Wi-Fi розетки и её состояние в приложении Tuya |
| Неоднозначный код / scale | Обезличенная спецификация на странице и явные настройки кодов |
| Сеть / timeout | Интернет, DNS, endpoint; после команды сначала обновите состояние |
| Уже выполняется запрос | Дождитесь текущего запроса, в том числе в другой вкладке |

Для неизвестного кода Tuya отображается код и общая подсказка. Произвольный текст ответа облака и исключения сетевого клиента не выводятся, поскольку могут содержать чувствительные данные.

## Структура для дальнейшего переноса

- `TuyaSigner`, `TuyaClient`, `CloudTransport` — подпись, токены, HTTP; здесь нет браузерной логики.
- `DeviceNormalizer` — чистое преобразование модели/показаний с точной десятичной арифметикой.
- `DeviceService` — снимок состояния, свежесть, блокировка операций, принятие и подтверждение команд.
- `Diagnostics` — безопасная проекция диагностических полей.
- `LocalController`, `LocalRequestFilter`, `static/` — локальный API и страница. Проверяются Host/Origin и пользовательский заголовок; CORS не разрешён. Глобального пользовательского OAuth и интеграции с my-items пока нет.

Локальные API: `GET /api/snapshot` (без обращения к облаку), `GET /api/queue` (статус подписки), `GET /api/events` (SSE, без облачного опроса), `POST /api/refresh`, `POST /api/relay` с `{"on":true}`. Для POST нужен `X-Local-Request: 1`. Состояние живёт в памяти до перезапуска.
